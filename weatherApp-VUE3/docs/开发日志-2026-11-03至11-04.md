### 生活指数改用图标表达好坏（放弃 CSS 配色）

前一日定下「桌面一行六列 / 移动两行三列」的布局后，用颜色区分好坏被否掉了。用户的理由是直觉性的：与其让「适合洗车」和「不宜洗车」只差一个色相，不如直接换图标——**能洗车就是 `car`，不能洗车就是 `car-off`**。

这个判断比配色方案更好，原因有三：
1. 色弱用户读不出色相差；
2. 六卡挤在一行时颜色面积太小，远看只像装饰；
3. 图标本身携带语义，不需要图例解释。

**落地做法**
- 图标库选 Tabler v3.50.0（6257 图标，MIT）。整包解压几十 MB，但只需要 20 多个，因此不装包，改成按需抓单文件。
- 可用的 CDN 只有一个：`https://cdn.jsdelivr.net/npm/@tabler/icons@3.50.0/icons/outline/<name>.svg`。`raw.githubusercontent.com` 取不到，npmmirror 的 unpkg 通道对 `@tabler/icons` 返回 403（`"@tabler/icons" is not allow to unpkg files`），`api.tabler.io` 域名不存在。
- 抓下 23 个 SVG 后转成纯 path 数据写进 `src/assets/icons.js`（用正则抽 `d` 属性，过滤掉背景用的 `M0 0h24v24H0z`），再从 `icons.js` 生成 `TablerIcon.vue`。这样避免运行时 `v-html`，也避免多一个 SVG 请求。

### 图标必须竖排——一个被宽度逼出来的决定

原本想让图标和文字同行（左图标右文字），量了宽度之后否掉了。

文本可用宽 = 单元格 − 2×border − 2×左右 padding：

| 视口 | 列数 | 单元格 | 文本可用宽 |
| --- | --- | --- | --- |
| 375/390（手机） | 3 | 107.67 / 109 px | **77.67 / 79 px** |
| 768–1023（平板） | 3 | 146.67 px | 116.67 px |
| 1024（桌面） | 6 | 152.67 px | **114.67 px** |
| 1280（桌面） | 6 | 195.33 px | 157.33 px |

7 字结论在 14px 下是 98px、16px 下是 112px。若图标同行，还要再加 24px（18px 图标 + 6px 间距）＝ 122/136px，在手机 79px、平板 116.67px、桌面 1024 的 114.67px 三档**全部折行**，手机从 2 行变 3 行。

改成竖排后宽度零新增，折行行为与改动前完全一致，只多约 22px 高度（grid 行高自适应，同行卡片自动等高）。于是定为 `flex-direction: column`。

### 折行调优：`text-wrap` 试错的三个回合

手机三列时「不宜久待户外」必须挤进一行 6 个汉字。做的调整：
- `.life-card` 左右 padding 从 14px 降到 **10px**，手机每卡 112.7px，扣掉 2×10 + 2px 边框剩 90.7px，刚好容下 6 个 14px 字（84px）。
- `.life-verdict` 从 15px 降到 **14px**。
- 宽度不够时 360px 级再加 `@media (max-width:400px)` 把左右 padding 降到 8px。

`text-wrap` 的三种取值都试过，结论是**必须两个一起用**：

| 尝试 | 结果 |
| --- | --- |
| `text-wrap: pretty` 单独 | 仍贪心断成 5+2 |
| `text-wrap: balance` 单独 | 把「适合户外运动」拆成「适合户 / 外运动」 |
| `word-break: auto-phrase` 单独 | 仍「适宜卫衣或 / 外套」 |
| **`auto-phrase` + `balance`** | **4+3 且不拆词** ✓ |

`auto-phrase` 负责按中文短语边界断，`balance` 负责把两行长度拉平——缺一个都不成立。

**实测**：320/344/360/375/390 稳定三列两行（360 起 6 字单行）；768 三列全单行；1024/1280/1440 六列全单行；`clippedX/Y` 全 false。

### 雷达降水地图调研

用户问能不能做小米天气 / 墨迹天气那种实时云雨图。

**核心事实：那些图的数据本身不开源。** 小米/墨迹的雨图来自商业数据源（华风、彩云、气象局雷达拼图反演）。交互可以复刻，数据必须换成开源源。逐个实测 HTTP 状态：

| 源 | 状态 | 特点 |
| --- | --- | --- |
| **RainViewer** | ✅ 可用 | 唯一真正免费的实时雷达，13 帧、过去 2 小时、10 分钟一帧 |
| NASA GIBS | ✅ 200 | 云量/真彩，**每天一张，非实时** |
| Himawari-9 (NICT) | ✅ 200 | 10 分钟一帧，但覆盖亚太，中国在边缘 |
| JMA nowc | ✅ 200 | **只覆盖日本** |
| 高德底图 | ✅ 200 | 浅色路网，**GCJ-02** |
| 天地图 | ❌ 418 | 需 token |
| OSM 官方瓦片 | ❌ 000 | 拒绝 |
| OpenWeatherMap | ❌ 401 | 需 key |

**坐标系是最大的坑**：RainViewer 是 WGS84，高德/腾讯/百度是 GCJ-02，直接叠加雨带会偏移 300–600 米。所以底图必须用 WGS84 的（这也是后来选 Esri 的原因之一）。

### 雷达 demo 三阶段重做

用户要求「加载 ruflo 技能，用 orchestrator 人格拆解，子任务用对应 ruflo 子人格指导，真正并行通过 DSH subagent 派发」。

**发现的底图问题（教训）**：第一轮 demo 用 CARTO 暗色底图，验证脚本报 PASS——但截图一看，底图全是「API KEY REQUIRED」水印。**CARTO 的免费暗色瓦片已经全线下线，HTTP 200 但返回的是水印图**。这说明 `curl -w %{http_code}` 返回 200 完全不能证明拿到了有效瓦片，**瓦片、图片类资源必须看画面验收**。

于是逐个试了 12 个候选底图，最后选 **Esri World Dark Gray**：唯一真正可用、暗色、且同为 WGS84 的免 key 底图。注意它的 URL 是 `tile/{z}/{y}/{x}`（**y 在 x 前**），与 Leaflet 默认顺序相反，写错就是错位。

Esri 暗色底图本身没有地名，于是自己加了 12 个主要城市的标注（`L.circleMarker` + `L.divIcon` 文字）。

**播放器的真实缺陷**：第 2 轮验证渲染正常但**屏幕上没有任何雨**。查 `performance.getEntriesByType('resource')` 发现 187 条 tilecache 请求全部 `transferSize: 0`（被中止），单个 `new Image()` 探测同一 URL 要 **1.3–12.4 秒**。

而播放器原本的逻辑是 `settle()` 绑在 `tileload`（第一块瓦片到就换帧）+ `FRAME_MS=520`——每 0.5 秒就把整层瓦片撕掉重建，永远加载不完。

三条修正：
- `LOAD_GUARD_MS` 480 → **15000**；新增 `FIRST_GUARD_MS = 6000`（首帧没有旧层可留，6 秒先亮已到的部分）。
- `showFrame()` 只保留 `layer.once('load', settle)`（**整层瓦片到齐才接管画面**），删掉 `tileload`。
- 新增 `armNextFrame()` 替代 `setInterval`：上一帧 `settle()` 之后才排下一拍，`state.pending` 时让位。

语义变成：**旧帧在整个等待期持续显示，新帧整层 load 完才交叉淡入**。网络慢只会让回放变慢，不会黑屏空转。

**另一个发现**：RainViewer 的 `color` 参数**完全无效**——`color=0…9` 对同一瓦片返回的字节数和 md5 完全一致（`25860` / `53dbe08b`）。所以配色改用前端 CSS filter 实现，并放弃 `hue-rotate`（绿色回波会变品红，单色相旋转破坏整条色带）。

图例色条也按瓦片真实像素重绘：写了个零依赖 PNG 解码脚本（`node:zlib` 手工解 IHDR+IDAT+反滤波）抽样，发现 RainViewer「通用」配色实际是 深蓝→亮蓝→浅青→黄→橙→红，**不是**绿→黄→红。

### 离线化与提速的基准测试

用户问「完全离线 + 雷达按需加载但要提高速度」怎么优化。写了一批基准脚本实测（`bench-radar/bench-ab/bench-fair/bench-static/bench-warm`）。

**确定性数据**（与网络抖动无关，可复现）：

| 项目 | 数值 |
| --- | --- |
| z4/z5/z6 瓦片 `cache-control` | `max-age=172800`（48 小时） |
| z7 瓦片 `cache-control` | `max-age=300`（5 分钟） |
| 同视野 512px | 30 块，单块 ≈ 28.7 KB |
| 同视野 256px | 108 块（4 倍），单块 ≈ 9.5 KB → **总流量更大** |
| 预热 13 帧（并发 8） | 25.5 s / 0.66 MB |
| 预热 13 帧（并发 12） | 18.9 s / 0.57 MB |
| 预热 13 帧（并发 16） | **12.8 s / 0.47 MB** |
| 预热后单帧换帧 | **1145 ms**（不预热是 3–7 s） |

**一次自我更正**：第一轮答复里我说「256px 比 512px 快 28%」，这是**测量错误**——那次对比让 256 多算了一级 zoom，覆盖范围和细节层级同时变了。已向用户明确撤回。教训：对比瓦片尺寸必须固定 URL zoom 和 z/x/y。

**关于抖动**：本机到 RainViewer 同场景耗时从 2.3 s 到 18.9 s 波动，**任何单次「快 X%」结论都不可信**，只能用多轮中位数，或者请求数/字节数这类确定性指标。

**`buildRainOutlook` 的关键设计**：如果传入的 hourly 数据整体已过期（`startIdx < 0` 或 `≥ limit`），返回 `ok:false, text:'暂无降水数据'`，而不是「未来 24 小时无雨」。理由是**不能把「没有数据」谎报成「确定没雨」**。所有 `null` 值也绝不参与数值比较。

**手绘 SVG 的一个技术选择**：最初用径向渐变做雷达斑块，但渐变是在 path 的 bbox（包围盒）里计算的，斑块一旦变扁，渐变边缘就提前淡出，看上去像「灰圈里点了颗小圆」。改成**同一形状按比例缩三层 + `feGaussianBlur`** 之后，多层永远跟着斑块轮廓走，才有雷达图上那种不规则等值线的感觉。

另外用 Vue 3.5 的 `useId()` 给每个实例生成独立 filter id，避免多个实例的 SVG filter 互相串台。

**测试 agent 抓到的真实 bug**：`TypeError: $setup.drift is not a function at RainForecast.vue:271`。

`drift` 是用 `computed` 定义的，但模板里写成了 `drift()`。Vue 的 computed 在模板里会自动解包成值，再调一次自然报「不是函数」。这个错误让整个 `.weather-content` 都没渲染出来（childCount = 0，连 hourly-section 都没有）。

改成 `drift` / `-drift` 后恢复正常。**这是个值得记住的坑**：模板里 computed 不加括号。

**lint 修复**
- `unicorn(no-new-array)`：`new Array(WINDOW_HOURS).fill(0)` → `Array.from({ length: WINDOW_HOURS }, () => 0)`。
- `unicorn(no-useless-spread)`：`for (const l of [...rainLayers])` → `Array.from(rainLayers)`。
- 46 个 `'process' is not defined` / `'Buffer' is not defined` 全来自 `ui-review/*.mjs`——这些是 Node 脚本，被 ESLint 当应用源码检查了。在 `eslint.config.js` 的 `globalIgnores` 加上 `'ui-review/**'` 解决。

## 这两日踩到的坑（汇总）

1. **HTTP 200 不等于内容有效**。CARTO 免费瓦片下线后仍返回 200，但内容是水印图。瓦片/图片必须看画面验收。
2. **ruflo 的 workflow 跑不了任务**。它需要各自的 LLM 后端，本机没有 key，`workflow_execute` 固定报 `requires config.agentId`。只能取它的人格与拆解范式，执行交给 DSH 原生 subagent。
3. **Vue 模板里的 computed 不加括号**。写成 `drift()` 会让整个区块不渲染，且错误信息只指向行号，不容易一眼看出。
4. **`text-wrap` 的中文断行要两个属性配合**。`auto-phrase` 管短语边界、`balance` 管两行等长，缺一个就会拆词或保持 5+2。
5. **对比实验必须控制变量**。瓦片尺寸对比时如果 zoom 不同，覆盖范围和细节层级会同时变化，得出的百分比毫无意义。
6. **单次网络测量不可信**。同一请求在 2.3–18.9 秒之间波动，只能看多轮中位数或请求数/字节数这类确定性指标。

### 真正值钱的七条技术结论

1. **拆 .vue 文件不省打包字节**。Vite/rolldown 只在 async import 边界切 chunk，
   同目录 SFC 互相 import 全进同一 chunk。要省字节只有 `defineAsyncComponent` 一条路，
   且必须同时加 `v-if` —— 否则 loader 在挂载时就触发，chunk 照样在首页下载。
   实测首屏 gzip 124,401 → 116,514（−6.3%）。

2. **补偿式交叉淡入**。两层线性淡入的 alpha 合成是 `1-(1-a1)(1-a2)`，中点最坏掉到
   稳定态的 64%，这才是闪烁的真正来源。改用 `a_new=1-(1-T)^w`、`a_old=1-(1-T)^(1-w)`
   后合成恒等于 T，与 w 无关。**第一次测法错误**：把各层 opacity 相加当浓度，得出
   「无凹陷」的假结论；alpha 合成是非线性的。

3. **`maxNativeZoom` 落在地图缩放空间**。`tileSize:512 + zoomOffset:-1` 时它比 URL
   层级大 1，填 7 只请求到 URL z6，URL z7 的真数据（4992B）被完全闲置。填 8 才对。

4. **`setLayerShift` 必须用 `getContainer()` 不能 `getPane()`**。Leaflet 所有
   `L.tileLayer` 共用同一个 `.leaflet-tile-pane`，平移它会把底图一起拖走
   —— 正是「平移方案被否决」的直接原因。

5. **中断的请求不进缓存**。Leaflet 换帧 `removeLayer` 会中止旧层瓦片，被中止的响应
   不写缓存，所以每圈都要重等 1.3–12 秒。预热必须用独立 `Image()` 加载。
   实测：第二圈换帧 8,050ms → 411–544ms。但**全量预热会反噬**：12 帧 × 30 块 = 360
   请求追不上 6.8 秒的播放节奏，还会抢当前帧连接（换帧新发请求 4→12–16 个）。

6. **渲染出来才叫验收**。CartoDB 免 key 瓦片已下线，但 HTTP 返回 200 + 合法 PNG
   + 2513 字节，内容是「API KEY REQUIRED」水印。中国天气网的雷达接口更隐蔽：
   200 + CORS + 233 帧 JSONP，数据停在 2023-01-03，图片全 404。
   **HTTP 状态码和 PNG 头都不能证明瓦片有效。**

7. **验证脚本的等待条件最容易写错**。`verify-rain-item` 原来只要 `.weather-content`
   出现就跳出等待，移动端接口慢时后续断言全打空 DOM。正确做法是等「目标元素出现
   或明确错误态」：`if (state === 'complete' && (item || error)) break`。
   另外 headless Edge 默认 `prefers-reduced-motion: reduce`，会让淡入直接跳到终值，
   必须 `Emulation.setEmulatedMedia` 显式改掉，否则永远测出单层。
