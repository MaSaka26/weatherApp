### 天气应用迁移到 Vue 3

- 将 `weather.html`（单文件原生实现，含大量 Trae/IDE 注入样式）迁移到 `weatherApp-VUE3`（Vite 8 + Vue 3.5 + Pinia + vue-router）。
- 原应用自身样式仅 `weather.html` 第 6–423 行，已抽离为 `src/assets/weather.css` 并在 `main.js` 全局引入；第 424 行之后为 IDE 注入代码，未迁移。
- 结构：
  - `src/api/weather.js`：Open-Meteo 地理编码 / 预报请求、22 个主要城市表、Haversine 就近估算
  - `src/utils/weatherCodes.js`：WMO 天气码 → emoji 图标 / 中文文案 / 天空背景 class
  - `src/stores/weather.js`：位置、数据、loading/error/success 状态、loadCity / loadByGeolocation / refresh / retry
  - `src/components/`：SkyBackground、SearchBar、LoadingState、ErrorState、CurrentWeather、DetailCards、HourlyForecast、DailyForecast、RefreshButton
  - `src/views/WeatherHome.vue`：页面组装
- 视觉与行为保持与原版一致；成功渲染用 `renderKey` 重建 DOM 以重放 fadeUp 动画；逐小时仍自动滚动到“现在”。
- 验证：`npm run build` 通过；CDP 伪造定位实测 24 条逐小时、16 天预报、天空背景 `clear-day`、控制台零错误。
- 已知遗留（沿袭原版）：`toISOString()` 判断“今天”存在 UTC 时区偏差；反向地理编码仍是内置城市表近似（150km 内）。

### 接入真实反向地理编码

- `api/weather.js`：新增 `reverseGeocode()`（BigDataCloud 免费免 Key，`localityLanguage=zh`，6s 超时）；`suggestNearestCity()` 拆为 `findNearestCity()`（返回 `{name,distanceKm}|null`）与 `formatCoords()`（正确区分 N/S、E/W）。
- `stores/weather.js`：地名解析改为「本地兜底先行 + 异步精修」——先用 `localLocationName()` 同步给出「附近：城市」或坐标并立即渲染天气，再异步反查，成功后回填真实地名；用 `placeToken` 令牌防止旧请求覆盖新定位/搜索结果。
- 实测该接口耗时波动较大（0.9s~6s+），因此不能阻塞首屏；`localityLanguage=zh` 偶发超时属正常，已由本地兜底承载。
- 顺带修正：定位错误码 3 单独提示「定位超时」，天气请求失败不再误报为定位超时。
- 验证：南通坐标显示「南通市」；拦截反查接口后南京显示「附近：南京」、青海偏远点显示「35.0°N, 100.0°E」。

### 地名渲染改为一次性（修复闪烁）

- 问题：先渲染兜底经纬度、约 1s 后被异步地名替换，视觉跳变。
- 改法：`loadByGeolocation` 改为 `Promise.all([fetchWeather, resolvePlace])`，全部就绪后 `showContent()` 一次性渲染，不再二次替换；`resolvePlace()` 永不 reject。
- 配套优化：反查超时 6s → 2.5s；新增 `weather:place-cache:v1` localStorage 缓存（约 1km 网格、24h、最多 50 条），重复访问命中缓存。
- 实测（预热后）：首次 0.5–1.6s，缓存命中 0.6s，城市名采样序列仅 `[null, "南通市"]`，无中间态。

### 地名反查改为本地城市表（彻底解决慢/显示坐标）

- 现象：把 BigDataCloud 超时压到 2.5s 后，首次加载频繁超时 → 只剩兜底坐标，用户反馈「只显示经纬度」。
- 实测该接口耗时极不稳定：3.4s / 4.7s / 1.1s / 0.3s，甚至 15s 超时；Photon、Nominatim 在本机均超时或返回空。
- 方案：内置中国地级行政区坐标表 `src/data/china-cities.json`（290 条，12KB，来源 npm 包 astrology-china-locations，MIT，源自 NGA GNS + 行政区划）。
- `api/weather.js`：`MAJOR_CITIES`/`findNearestCity` 替换为 `CHINA_CITIES`/`findLocalCity(lat, lon, maxKm)`；BigDataCloud 仅作境外/无覆盖兜底（5s，超时不 abort，跑完写缓存）。
- `stores/weather.js`：`resolvePlace()` 三级——本地 60km 内直接用城市名 → 本地 150km 内显示「附近：X」→ 联网反查 → 坐标。
- 实测：南通 1284ms、北京 972ms、昆山 644ms（显示苏州），三者均 0 次联网；青海偏远 674ms 联网 1 次返回「海南藏族自治州」；序列仍为 `[null, 城市名]`，无闪烁。
- 已知取舍：只到地级市精度，县级市会显示所属地级市（昆山→苏州）。

### 地名精度升级为区县级（修复「在松滋显示附近：宜昌」）

- 根因：旧的 290 条地级市表**缺荆州市**（源包行政数据里荆州无坐标被丢弃），松滋最近的地级市被算成 79km 外的宜昌；且只到地级市，无法表达县级市。
- 新数据 `src/data/china-places.json`：`{c:[name,province,lat,lon], d:[name,cityIdx,lat,lon]}`，**394 地级 + 2814 区县**（111KB，gzip 40KB）。来源为阿里 DataV.GeoAtlas 行政区边界中心点（`geo.datav.aliyun.com/areas_v3/bound/{adcode}_full.json`，逐省→逐市抓取后固化，运行时零网络）。
- `src/utils/placeLookup.js`：`lookupPlace()` 在区县+地级全集里取最近单位；区县≤45km→区县名，地级≤60km→市名，≤200km→「附近：X」，否则 null 交给联网兜底。**市辖区显示上级市名**（东城区→北京）；**不设区的地级市**（中山/仙桃等）若城市中心比任何区县近则直接用市名，避免被邻市辖区抢走。
- `stores/weather.js` 新增 `cityDetail`：区县显示「省 · 地级市」，地级显示省，搜索结果显示 admin1；`CurrentWeather.vue` 增加 `.current-region` 副标题行，`weather.css` 加对应样式。
- `api/weather.js` 删除 `MAJOR_CITIES/findLocalCity/haversineKm`，`geocodeCity` 补 `admin1`。
- 实测（生产构建）：松滋市区/刘家场/卸甲坪 → 松滋（湖北省 · 荆州市）；中山 → 中山；仙桃 → 仙桃；北京 → 北京；昆山 → 昆山（江苏省 · 苏州市）；青海玛多 → 玛多（青海省 · 果洛藏族自治州）。地名采样序列仍为 `[null, 地名]`，无闪烁。
- 抓取注意：DataV 并发>10 会 403 限流；无下辖区县的城市返回 404（需当作叶子节点处理，不能重试）。

### 修「设置里的描边和毛玻璃看不出变化」

- **量化结论**（CDP 逐像素 A/B，取局部裁剪区）：原始实现下 `--glass-scale` 0→1.6 的像素差 **mean 0.01 / 0% 像素超阈值**，等于没生效；描边 0→1 只有 6.4% 像素变化且集中在 emoji 边缘一圈。
- **根因**：① `backdrop-filter` 只模糊卡片背后的内容，而背后是平滑天空渐变，模糊纯渐变 = 无变化；② 描边色 `rgba(10,20,36,.5)` 是深藏青，背景也是深藏青，深压深看不见。
- **描边改法**：宽度由 px 改 `0.065em` —— 22px 图标得 1.43px、11px 数字得 0.7px，一份 token 按字号自动收放；颜色加深到 `rgba(6,14,26,.82)`。实测 2.2px 以上 emoji 像黑贴纸（Segoe 的 ☁️ 自带细黑边，1.2–1.8px 才是「清晰」区间），故 0.065em × 档位 1.6 = 2.3px 作为「加重」上限。
- **毛玻璃改法**：档位同时驱动两层背景图 —— `--glass-frost`（白雾，`max(0,(1-scale)*.12)`，关掉时 12% 白雾 → 卡片变实）与 `--glass-shade`（暗纱，`max(0,(scale-1)*.2)`，调高时更暗 = 更通透，因为背景是深色）。标准档两层都是 0，默认外观零改变。
- 应用选择器：`.detail-card / .hourly-scroll / .daily-list / .dc-wrap / .view-switch / .search-input / .refresh-btn / .settings-btn`，且必须放在所有 `background` 简写之后（简写会把 background-image 重置为 none）；同时把 `.detail-card:hover`、`.search-input:focus`、`.refresh-btn:hover` 三处的 `background:` 改成 `background-color:`，否则 hover 时雾层消失。
- 复测：毛玻璃 0↔1 mean 18.4 / 86% 像素，0↔1.6 mean 24.9 / 87%；描边 0↔1 环状区域 1.7%（环本身很细，属正常几何），肉眼对比截图差异明确。
- 顺带确认：headless 截图必须开 `Emulation.setTouchEmulationEnabled`，否则 `pointer:fine` 会让横向滚动条压住曲线视图最后一列文字，看起来像布局 bug。

### 描边「关不掉」的真正原因：emoji 字形自带黑边

- 用户反馈切换「关」后 16 天列表与所有天气图标仍有描边。实测 `.day-icon` / `.hour-icon` 在档位 0 时 `--outline-w` 算成 0px，但**仍有残影**：8 个 0 偏移、0.82 不透明的 text-shadow 会压在字形反锯齿边缘上（实测 0.28% 像素、最大差 38）。
- 修法：`--outline-color: rgba(6, 14, 26, calc(0.82 * min(1, var(--outline-scale))))`，档位 0 时 alpha 归零，实测计算值 `rgba(6, 14, 26, 0) 0px 0px 0px`，等于什么都不画。（`calc()` + `min()` 写在 rgba 的 alpha 里 Chrome 完全接受，`--glass-frost` 同款写法也早已验证可用。）
- **但真正让用户觉得「没消失」的是字形本身**：同一张对照图里，完全不给 text-shadow 时 `🌧` 边缘干净、`☁️` 和 `⛅` 仍自带一圈黑边 —— 若是我们的阴影，所有图标应该一样。Segoe UI Emoji 把白底云朵画成了描黑边的图案，20px 下那圈边约 1–1.5px，和我们的「标准」档 1.3px 几乎重合，所以开关看不出差别。
- **结论：emoji 方案下「关掉描边」在物理上做不到**。唯一真解是自绘图标（SVG），描边改 `filter: drop-shadow(0 0 Npx ...)`，档位 0 时 filter 直接 none。
- 已做方向预览 `ui-review/icon-preview.html` + `icon-compare.png`：9 个自绘图标（晴/晴夜/阴/多云/雨/毛毛雨/雪/雷暴/雾）× 无描边/有描边，40px 放大对照 emoji。自绘行无描边时完全干净。
- 20px 图标判据补充：这段尺寸的 emoji 自带边 ≈1–1.5px，任何加在 1–1.5px 的描边都会与它并成一条，只在 2px 以上才有明显差别（但 2px 会很「贴纸」）。
